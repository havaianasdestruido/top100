WebMCP: AI agent tools for this site

Top100 is an ordinary static website — and a WebMCP client-side MCP server for the same content. An AI agent running in the browser can discover 16 tools here and call them directly instead of scraping the tables, with the results the page itself would have produced.

  • 16 WebMCP tools
  • 14 read-only
  • 8 return GitHub text
  • 3,000 repositories reachable
  • Same-origin only, no cookies

Try the tools in this tab

The fastest way to see WebMCP working is the debug panel on this site: it lists every registered tool with its JSON Schema and lets you call it by hand, through exactly the same validation, rate limiting and output budget an agent's call goes through.

  • Open the homepage with the debug panel
  • Open a language page with the debug panel

To drive the tools with a real agent, enable WebMCP in your browser:

  • Chrome: chrome://flags/#enable-webmcp-testing → Enabled, then relaunch. Some builds instead run the origin trial; the site works with either.
  • Agent extensions: the Model Context Tool Inspector lists the tools and calls them with a prompt.
  • CLI agents: agent-browser announces WebMCP tools automatically and can invoke them with agent-browser webmcp invoke.
  • No browser support? This site ships its own polyfill, so the tools register anyway — see the polyfill section below.

Security model

WebMCP tools are code the page runs on the agent's behalf, so the interesting questions are what a tool can reach, what it can change, and what a hostile string could do once it is inside a model's context. The answers here are deliberately boring.

What this site does about each WebMCP risk, and where the code lives.
RiskMitigation on this site
Cross-origin reachTools are registered without exposedTo, so only this origin can see or call them. Registration is skipped entirely inside a cross-origin iframe unless the embedder granted allow="tools".
Malformed or hostile argumentsEvery call is validated against the tool's JSON Schema before it runs: types, ranges, enum membership, 200-character string caps, array length caps, four levels of nesting. Unknown arguments are ignored and reported back.
Prototype pollution__proto__, prototype and constructor are rejected anywhere in an argument tree, and validated values are copied into a fresh object.
Runaway agents90 calls per minute per document, 30 per tool, a 100 ms minimum gap, one in-flight call per tool, and an 8-second timeout (15 s for the three tools that read a dataset file) wired to AbortSignal.
Context floodingResults are capped at 1500 characters. Array payloads are shrunk until the envelope fits and the result says exactly how many items were dropped.
Prompt injection from repository textDescriptions, topics and names come from GitHub, so any tool that returns them declares untrustedContentHint: true and every result carries "trust": "untrusted" with a note. Control characters are stripped and every free-text field is length-capped. Nothing on this site asks an agent to run a command, reveal a secret or trust a suggestion.
Data exfiltrationThe only network calls are same-origin GETs of files under data/, with credentials omitted, redirects refused and a 4 MB ceiling. No cookies, no analytics, no third-party requests, no sendBeacon.
Injection into the pageTool results and tool names are rendered with textContent; innerHTML and eval are never used anywhere in the WebMCP code, and the build fails a test if they appear.
Silent automationTools act on the visible page and report what they did: a live region announces every call, and the tools that change the page (filter_repository_table, open_page) are the only two that are not read-only. Both are annotated accordingly.

Every tool

Annotations follow the WebMCP annotations object: readOnlyHint means the tool does not change anything, untrustedContentHint means its result contains third-party text, and consequentialHint — never set here, because nothing on this site books, buys or deletes anything — would ask for user confirmation.

How the runtime works

assets/webmcp-core.js does three things, in this order:

  1. Use what the browser has. If document.modelContext exists (or the older navigator.modelContext from the origin-trial builds), the tools are registered there, unchanged.
  2. Otherwise install a polyfill. A dependency-free implementation of the same surface — registerTool, getTools, executeTool, provideContext, the toolchange, toolactivated and toolcancel events, and unregistration through an AbortSignal — is installed on document.modelContext. It never replaces a real implementation, and it refuses to install on an insecure origin or in a cross-origin frame without permission.
  3. Wrap every tool in the same guard. The validation, rate limiting, timeouts, output budget and envelope formatting live inside each tool's execute(), so an agent that calls the native executeTool gets exactly the same guarantees as one that calls the polyfill.

Two URL parameters exist for testing, and neither is read by anything else: ?webmcp_debug=1 opens the debug panel, and ?webmcp_polyfill=1 forces the polyfill even where the browser has native support.

Tools are registered per page. A language page registers the tools that make sense for its 100 rows; the FAQ page registers the documentation tools; nothing registers a tool it cannot answer. The manifest of what is available where is published as data/webmcp-manifest.json.

For agents that never open the page

WebMCP's own discoverability limit is that a client has to visit a page to know what it offers. Two static artifacts cover the gap:

  • data/webmcp-manifest.json — every tool with its full JSON Schema and annotations, the runtime facts, the security model, and SHA-256 checksums for all 30 JSONL files.
  • llms.txt and llms-full.txt — the same site described for agents that read text instead of calling tools.

Limitations, stated plainly

  • WebMCP is an early standard. The API shape is still moving; this site supports both document.modelContext and the earlier navigator.modelContext, and degrades to its own polyfill when neither exists.
  • A page must be open for its tools to exist. Nothing here works headless unless the HTML is actually loaded in a browser.
  • Tool results are for one page's worth of context. Deep analysis across all 3,000 records belongs in the JSONL files, not in a tool result.
  • readOnlyHint and friends are declarations, not enforcement. They are accurate here, but a client should treat every page's claims as untrusted — as OpenAI's and agent-browser's own documentation says.
  • Tools read the dataset snapshot embedded in the page or committed to the repository. Between refreshes, they are as stale as the timestamp at the top of every page.

Questions about the tools

Do I need a browser extension?

No. Any browser with WebMCP support exposes these tools to whatever agent is running there; the extension is only a convenient way to test.

Does this change how the site works for people?

No. Every page is complete HTML before any script runs, the WebMCP code adds a small collapsible panel and nothing else, and with JavaScript off the site is byte-for-byte the site it was.

Is anything tracked?

No cookies, no analytics, no third-party requests. The only network traffic the tools generate is this site fetching its own data files.
